# Liora UI Rules

## 1. Продуктовое ощущение
1. Приложение и лендинг — один мир: мир карточек. Карточка для учёбы нарисована как настоящая линованная index card с красной линией под заголовком, её оборот — синяя карточка с лендинга. Оценки — наклеенные стикеры.
2. Экран Learn — это стол с одной карточкой: очередь, карточка, оценки под ней, стопка «done» на широких экранах. Ничего, что не помогает учить эту карточку, на этом экране нет.
3. Остальные экраны спокойные: тот же шрифт, цвета и клавиши, без украшений.
4. Нельзя собирать интерфейс как админ-дашборд: без коробки вокруг страницы, без «коробки в коробке», без декоративных бейджей (дата в шапке и т. п.). Рамка только у того, что само является объектом: таблица, карточка, форма.
5. Каждый экран сразу отвечает на 3 вопроса: где я, что могу сделать, что сейчас важно.
6. Нельзя использовать визуальный шум: без градиентов и свечения. Глубину дают края и мягкая тень под карточкой.

## 2. Визуальный язык
1. Подпись стиля — «клавиша»: рамка 2px и более толстый нижний край (`--edge-width`, 4px) более тёмного оттенка. Всё, что нажимается, выглядит как клавиша.
2. Hover поднимает клавишу (translateY(-1px), край толще на 1px), нажатие опускает её (translateY(2px), край 2px, 60ms). Hover-правила только внутри `@media (hover: hover)`.
3. Панели и карточки — рамка 2px `--color-border`, радиус `--radius-panel` (20px), без тени. Контролы — радиус `--radius-control` (12px).
4. Тени только у плавающих слоёв: модалки, меню, тултипы, тосты.
5. Главный акцент — синий `--color-primary`. Цвета оценок — отдельная семантика:
   - Again — красный `--color-grade-again`, он же цвет опасных действий;
   - Hard — янтарный `--color-grade-hard`, он же предупреждения;
   - Good — синий `--color-grade-good`;
   - Easy — зелёный `--color-grade-easy`, он же успех.
   У каждого есть `-edge`-оттенок для нижнего края.
6. Контраст текста должен быть выше контраста декоративных элементов.

## 3. Токены и стили
1. Нельзя использовать raw-цвета в компонентах, только токены.
2. Нужно разделять базовые токены и семантические токены.
3. Размеры, отступы, радиусы, тени и z-index задаются только через шкалы токенов.
4. Цветовые токены должны поддерживать тему light, dark и system.
5. Имена токенов должны быть стабильными и предсказуемыми.

## 4. Типографика
1. Одна гарнитура на всё — Nunito (`--font-ui`), подключена через `@fontsource-variable/nunito` в `src/app/App.jsx`. Кнопки и поля наследуют её.
2. Шкала размеров и line-height должна быть фиксированной, без случайных значений.
3. Веса: заголовки 900, кнопки и то, что нажимается, 800, подписи и метки 700–800, основной текст обычный.
4. Основной текст должен быть легко читаемым и менее плотным, чем заголовки.
5. Подписи и мета-тексты всегда менее контрастные, чем основной текст.
6. Ширина строк должна оставаться комфортной для чтения.

## 5. Сетка, отступы и ориентации
1. Нужно использовать единую шкалу отступов на всем проекте.
2. Три формы каркаса, по тому, как держат экран:
   - широкий экран и планшет — узкая колонка навигации слева (иконка и подпись);
   - телефон вертикально (`(max-width: 720px) and (orientation: portrait), (max-width: 540px)`) — таб-бар снизу;
   - телефон горизонтально (`(orientation: landscape) and (max-height: 540px)`) — колонка слева, только иконки, чтобы не терять высоту.
3. Каждый экран проверяется во всех трёх формах и на 2560 px. Горизонтальной прокрутки страницы быть не должно.
4. Контейнер, который растягивается по высоте, должен иметь `min-height: 0`; флекс- и грид-обёртки не должны расширяться по содержимому (`minmax(0, 1fr)`, `min-width: 0`).
5. Карточка в Learn размеряется от своего контейнера (container queries), а не от окна: самая большая карточка нужной формы, которая помещается вместе с оценками. 5:3 на широком экране, вертикальная на вертикальном контейнере, не шире 1440 px. Текст внутри — в единицах `cqi` карточки.
6. На мобильных обязательно учитывать safe-area со всех сторон.

## 6. Навигация
1. Навигация должна быть предсказуемой и одинаковой по паттернам на всех страницах.
2. Активный раздел должен быть визуально очевиден в любой момент. Он отмечается залитой синей иконкой и короткой синей меткой у края: слева в колонке, сверху в нижней панели. Никаких подложек и рамок вокруг выбранного пункта.
3. Клик по активной вкладке не должен вызывать лишний ререндер и перезагрузку данных.
4. Мобильная навигация должна работать плавно без задержек и ложных состояний.
5. Иконки и текст в навигации должны быть строго выровнены.

## 7. Кнопки и действия
1. Кнопки берутся из `@shared/ui` `Button`: primary (синяя залитая клавиша), secondary (белая клавиша с синим текстом), ghost (без рамки), danger (красная клавиша).
2. В каждом блоке только одна primary-кнопка; она обозначает действие, ради которого существует экран (Save deck, Open, Import to Decks).
3. Оценки — `SrsRatingControls` с `variant="stickers"`: четыре стикера в цветах оценок, в одном порядке (Again, Hard, Good, Easy), со слегка разным наклоном. Клавиша оценки показана в углу стикера и скрыта на тач-экранах.
4. На телефоне тулбар — одна строка (при нехватке места прокручивается вбок), а не колонка кнопок на всю ширину. Второстепенные действия — клавиши-иконки с доступным именем.
5. Для всех кнопок обязательны состояния default, hover, active, focus, disabled, loading. Focus — outline 3px `--color-primary-border`.
6. Для опасных операций нужен явный confirm.

## 8. Формы
1. Обязательно использовать семантические теги form, label и button type="submit".
2. Enter должен отправлять форму в ожидаемом контексте.
3. Label обязателен для каждого поля, placeholder не заменяет label.
4. Ошибки валидации должны показываться рядом с полем и понятным языком.
5. Тексты в чувствительных разделах должны объяснять текущее состояние пользователя.
6. Нужно использовать корректные значения autocomplete.

## 8a. Настройки
1. Каждая настройка — строка `SettingRow` из `@shared/ui`: слева название и одна строка подсказки, справа контрол. Строки собраны в группы `SettingGroup`. Если в группе одна строка или название группы повторяет название раздела, заголовок группы не ставится.
2. Контролы выбираются по данным:
   - вкл/выкл — `SettingSwitch`;
   - 2–6 коротких вариантов — `SettingSegmented`;
   - число — `SettingStepper` с кнопками − и +;
   - длинный список — `SettingSelect` (внутри это `Select`);
   - свободный текст — поле на всю ширину строки (`wide`).
3. Подсказка объясняет, что изменится, и берётся из того, как код работает на самом деле. Если поведение не проверено, подсказки нет.
4. Раскладка зависит от ширины, которую получили настройки (container queries):
   - широко — список разделов слева и открытый раздел справа;
   - узко — один экран за раз: список, потом раздел с кнопкой «All settings».
   Раздел открывается ссылкой `?tab=`, поэтому кнопка «назад» в браузере работает.
5. В списке разделов под названием каждого раздела видны его текущие значения (`buildSettingsSummaries`).
7. Аккаунт — не одна из настроек: он стоит отдельной синей карточкой над поиском и списком разделов.
6. Поиск ищет по названиям, подсказкам и ключевым словам всех разделов сразу. Совпадение с названием группы или раздела показывает её целиком. Всё, что не является строкой, оборачивается в `SettingContent`.

## 8b. Выпадающие списки
1. Нативный `<select>` в интерфейсе не используется, вместо него `Select` из `@shared/ui`. Варианты передаются как у нативного: дочерними `<option>`. `onChange` получает `{ target: { name, value } }`.
2. Закрытый список выглядит как «клавиша». На компьютере он открывается карточкой под полем или над ним, если снизу не хватает места. На телефоне открывается шторкой снизу с крупными пунктами.
3. Выбранный пункт отмечен синей меткой и галочкой. При 9 и больше вариантах сверху появляется поиск. На телефоне поиск получает фокус только по нажатию, чтобы клавиатура не закрывала список.
4. Открытый список рендерится через портал в `body`: `position: fixed` внутри container query или трансформированного предка считался бы от предка, а не от окна.
5. Клавиатура: стрелки открывают список и двигают выбор, Enter выбирает, Esc закрывает только список (не диалог вокруг), Tab уходит дальше. Набор букв переходит к совпадающему пункту и на закрытом поле.

## 8c. Прогресс и графики
1. Все числа страницы прогресса считает одна чистая функция `buildLearningStats` из `@shared/core/usecases/progress`. Веб (IndexedDB) и десктоп (SQLite) только достают сырые строки и отдают их ей. Второй реализации подсчёта нет.
2. Не выдумывать данные. Если данных нет, показывается пустое состояние с тем, что сделать дальше. Никаких «примерных» процентов.
3. Главное на странице — число известных слов на учётной карточке, как на экране Learn. Остальные блоки — тихие карточки: один график и его числа.
4. Цвета графиков берутся только из токенов `--chart-*`, проверенных валидатором палитр. Одна синяя шкала (`--chart-ramp-1..4`) означает «больше» или «дальше». Незаполненная дорожка (`--chart-track`) означает «ещё не начато». Для ответов используются тона `--chart-grade-*`. Текст никогда не красится в цвет серии.
5. У графика с двумя и больше сериями есть легенда с числами. Между сегментами оставляется зазор 2px. У каждого графика есть `role="img"` с описанием, а у календаря активности — скрытая таблица.
6. График — одна остановка Tab. Стрелки переходят по меткам, указатель наводит, тап выбирает. Подсказка одновременно служит live-регионом. Позиция подсказки меряется в обработчике события, а не в эффекте.
7. Календарь активности показывает столько недель, сколько помещается: 17, 26, 39 или 53. Недели отбрасываются целыми столбцами через `data-age` и container query.
8. Раскладку определяет ширина страницы (container query на `.progress`), а не окно.
9. Карточки на странице прогресса не меняют высоту от объёма данных. Колоды идут страницами по 6 в выбранном порядке (Active / Due / A–Z, порядок запоминается). У каждой строки одна высота, длинное название обрезается многоточием (полное название в `title`). Короткая последняя страница держит место полной. В широкой карточке колоды идут в две колонки. Больше колод — больше страниц, а не длиннее карточка.

## 8d. Стикеры (ачивки)
1. Стикеры считает `buildAchievements` из тех же данных, что и страница прогресса: 8 семейств, у каждого ступени. Каждая ступень заработана числом, которое пользователь может проверить сам. Ачивок «за просто так» нет.
2. Всё, что считается по журналу повторов (серия, дни, повторы, большой день, чистый лист), датируется днём, когда порог был пройден. Всё, что считается по словам как они есть сейчас (словарь, долгая память, освоенные колоды), не датируется и может снова упасть. Такие стикеры сохраняются в журнале устройства (`localStorage`, отдельно для каждого профиля) и датируются днём, когда устройство впервые их увидело. В подписи это различается: «Earned on» и «Earned by».
3. Заработанный стикер — цветная вырезка с белой кромкой, наклеенная чуть криво. Незаработанный — пунктирное место в альбоме, ровное. У следующего по очереди место заполняется полоской прогресса в цвете семейства. Новые стикеры с прошлого визита «прилепляются» с анимацией и меткой New. При `prefers-reduced-motion` анимации нет.
4. Цвет семейства задаётся токеном `--sticker-*`. Белый текст на нём должен иметь контраст не ниже 4.5:1. Семейство всегда узнаётся ещё и по иконке и названию, а не только по цвету.
5. У серии прогресс к следующей ступени считается по текущей серии, а у остальных семейств — по общему значению.

## 8e. Аккаунт: карточка ученика
1. Аккаунт показан как карточка ученика (`AccountCard`): имя, email, «member since», номер карты из id аккаунта, три числа (знакомые слова, серия, стикеры), 12–17 недель активности и три последних стикера, наклеенных на угол. Числа берутся из тех же данных, что и страница прогресса, стикеры — из общего журнала `@shared/lib/stickers`.
2. Карточка наклоняется за мышью с бликом. Наклон и блик обновляются раз в кадр (`requestAnimationFrame`), только через `transform` отдельных слоёв: без перерисовки React и без перерисовки карточки. Переворот рисует всегда одну сторону: карточка уходит на ребро, сторона меняется, и она возвращается. `backface-visibility` не используется, потому что Firefox-движки его здесь не соблюдают. При `prefers-reduced-motion` наклона и блика нет. Переворот доступен кнопкой под карточкой (`aria-pressed`) и кликом по карточке. На обороте — магнитная полоса, что аккаунт позволяет сейчас, и полоса подписи.
3. Пока пользователь не вошёл, карточка пустая и пунктирная и заполняется по мере ввода в форму. Если email не подтверждён, на карточке стоит штамп, а в статусе рядом — кнопка отправить письмо ещё раз.
4. Размеры внутри карточки задаются в `cqi`, поэтому это одна и та же карточка на телефоне и на мониторе. Мелкий текст ограничен снизу через `max()`, а на узкой карточке активность сокращается до 12 недель.

## 8f. Синхронизация в интерфейсе
1. Фоновая синхронизация каждые несколько секунд — не новость. Статус пишет «Syncing» только для синхронизации, запущенной вручную, или для самой первой. В остальное время там «Synced», а ошибки и офлайн видны сразу. Кнопки и подписи не мигают от фоновых проходов.

## 9. Таблицы, списки и карточки
1. Заголовки колонок и действия должны быть строго выровнены.
2. Клик-зона строки должна быть предсказуемой и одинаковой для всех строк.
3. Меню действий через многоточие используется только когда это улучшает сканирование.
4. Поиск, фильтры и счетчики должны быть компактными и читаемыми.
5. Тултипы и меню не должны обрезаться контейнерами.
6. Пагинация должна быть понятной и доступной с клавиатуры. Везде используется один компонент `CardCatalogPagination`. Если места мало (container query), он сворачивается до «назад / Page N of M / вперёд» и не переносит ряд номеров страниц. Номер страницы списка хранится в адресе (`?page=`), поэтому после возврата из карточки открывается та же страница. Поиск и смена размера страницы возвращают на первую страницу, а страница, которой больше нет, прижимается к последней (`paginate` из `@shared/lib/pagination`).

## 10. Тултипы, поповеры и модалки
1. Нельзя использовать системный title для важных подсказок.
2. Кастомный тултип должен иметь корректный слой и не перекрываться таблицей.
3. Стрелка тултипа должна быть геометрически привязана к триггеру.
4. Модалка должна иметь фокус-трап и корректное закрытие по Escape, если это безопасно.
5. Оверлеи не должны мерцать или прыгать при скролле.

## 11. Состояния и обратная связь
1. Для каждого ключевого сценария обязательны состояния loading, empty, error, success.
2. Ошибки должны объяснять что произошло, почему и что делать дальше.
3. Статусы не должны исчезать слишком рано.
4. Локальные ошибки показываются рядом с контекстом, а не только глобально.
5. После важного действия пользователь должен видеть явный результат.

## 12. Анимации и производительность
1. Анимации рассказывают, что случилось с карточкой: переворот — поворот в 3D; оценка Hard/Good/Easy — карточка улетает в стопку «done»; Again — ныряет обратно под очередь; просмотр — уезжает вбок; следующая карточка поднимается со стопки.
2. Уходящая карточка рисуется копией (`useLeavingCard`), логика оценки её не ждёт. Если анимация не запустилась, копия снимается по таймауту.
3. Пружинная кривая `--motion-spring` — для подъёма, нажатия и появления. Цвета меняются обычным ease.
4. Нельзя использовать анимации, которые блокируют ввод. Анимируются только transform, opacity и ширина нижнего края.
5. `prefers-reduced-motion: reduce` убирает движение. Анимации, от конца которых что-то зависит, заменяются коротким fade, чтобы событие конца всё равно пришло.

## 13. Адаптив и мобильный UX
1. Интерфейс должен корректно работать в portrait и landscape.
2. Нужно учитывать safe-area со всех сторон, включая устройства с вырезами.
3. Нельзя допускать случайный zoom при вводе и при смене ориентации.
4. Минимальный touch target для интерактивных элементов должен быть 44x44.
5. В мобильном режиме ключевые действия должны быть в приоритете.

## 14. Доступность
1. Контраст текста и интерактивов должен соответствовать WCAG.
2. Видимый focus-ring обязателен для клавиатурной навигации.
3. Для tabs, menu, tooltip и modal обязательны корректные ARIA-атрибуты.
4. Tab-order должен быть логичным и без ловушек.
5. Иконки без текста должны иметь aria-label.

## 15. Тексты и microcopy
1. Тексты должны быть короткими, конкретными и без лишнего технического жаргона.
2. Кнопки должны называться действием, а не абстрактными словами.
3. Формулировки не должны пугать пользователя без причины.
4. Текст должен снижать неопределенность и помогать принять следующее действие.

## 16. Definition of Done для UI-задачи
1. Изменение не ломает существующие сценарии.
2. Результат консистентен со всем интерфейсом Liora.
3. Проверено на desktop, mobile и landscape.
4. Проверена работа с клавиатуры и базовая доступность.
5. Проверены состояния loading, empty, error, success.
6. Формы корректно отправляются по Enter и валидируются до отправки.
7. Нет лишних ререндеров при повторных кликах по активным разделам.
8. Новые стили выполнены через токены и не нарушают визуальную систему.
