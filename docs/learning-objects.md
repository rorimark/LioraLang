# Liora: от языковых карточек к личному приложению для запоминания

Статус: **этапы 1–3 реализованы** (см. §8–10). Этап 4 остаётся условным: независимые расписания требуют отдельной проверки потребности. Разделы 1–7 сохраняют первоначальный аудит и план.

## 1. Аудит: что есть сейчас

### Стек и платформы
- Vite + React 19, React Router 7, FSD-слои (`app → pages → widgets → features → entities → shared`), проверка направлений импортов `check:layers`.
- Две цели одной кодовой базы: web/PWA (IndexedDB, service worker, офлайн) и Electron (SQLite через better-sqlite3). Платформенные репозитории за общими интерфейсами (`usePlatformService`).
- Ядро в `packages/shared/src/core/usecases`: `cardContent`, `srs`, `importExport`, `sync`, `wordSuggest`, `hub`, `progress`. Чистые функции с тестами.

### Модель данных
- **Колода (deck)**: `name, description, sourceLanguage, targetLanguage, tertiaryLanguage, usesWordLevels, tags, pictureSide ("" | source | target), learnedSide ("" | target), syncId, originKind/originRef, contentHash`.
- **Запись (word)**: `source, target, tertiary, level (CEFR), part_of_speech, tags[], examples[], image {assetId, alt} | null, externalId`.
- **Карточка повторения**: одна на запись. Web: `reviewCards` с `keyPath: "wordId"`; SQLite: `review_cards.word_id UNIQUE`. Лог повторений `reviewLogs`.
- **Направление** (`source_to_target | target_to_source | mixed`) задаётся настройкой сессии и лишь выбирает, какая сторона спереди (`resolveCardFaces`). Своего расписания у направления нет.

### Механизмы, которые уже есть и переиспользуются
| Механизм | Где | Статус |
|---|---|---|
| SRS (FSRS-5, проверен против ts-fsrs) | `core/usecases/srs` | не трогаем |
| Типы содержимого стороны: TEXT / IMAGE | `cardContent.js` (`CONTENT_TYPES`, `buildSideContent`) | расширяем |
| Медиа: asset по SHA-256, оригинал/миниатюра, замена/удаление, sync, экспорт | `mediaRepository`, `mediaSync`, `deckPackage` | переиспользуем как есть |
| Синхронизация: колоды JSON-пакетами + события прогресса `(deck_sync_id, word_external_id)` + медиа | `sync/createSyncRepository.js` | переиспользуем |
| Экспорт/импорт `.lioradeck` / `.lioralang` / `.json`, хэш содержимого | `importExport/deckPackage.js`, `sync/deckIdentity.js` | расширяем полями |
| ИИ: edge function `suggest-word` (Gemini), задачи word/list/topic/hint/deck, квота 300/день, структурированный JSON, проверка на сервере и в клиенте, AbortController, «призрачные» подсказки, которые не перетирают введённое | `supabase/functions/suggest-word`, `features/word-suggest` | расширяем новой задачей |
| Learn: раскрытие ответа, оценки 1–4, клавиатура, анимации, подсказка после «Снова» | `widgets/LearnFlashcardsPanel`, `features/flashcard` | рендер расширяем, поток не трогаем |

### Что жёстко завязано на языки
- Колоду нельзя сохранить без двух языков (кроме стороны-картинки): `validateImportLanguages`.
- `level` = CEFR, `part_of_speech` = часть речи, `examples` = предложения на языке сорса.
- ИИ-задачи формулируют всё как перевод.
- Hub хранит языки колонками (`source_language`, `target_languages`).

## 2. Ответы на вопросы из §3

- **Что сейчас word, card, review unit?** Запись = объект знания; карточка = запись + направление сессии; единица повторения = запись (одна на запись).
- **Можно ли расширить без массовой переделки?** Да, если объект знания остаётся записью, а предмет задаётся колодой. Новые поля добавляются тем же путём, что `pictureSide` и `learnedSide`: хранятся только если не по умолчанию, поэтому старые колоды читаются, экспортируются и хэшируются как раньше.
- **Как представлены язык, изображение, старые карточки?** Язык — свойство стороны колоды. Изображение — содержимое стороны в колоде с картинками. Старые карточки — записи без новых полей.
- **Как связаны несколько представлений одного объекта?** Сейчас только через направление сессии (одно расписание). См. §4.
- **Как scheduler идентифицирует review unit?** По `wordId` локально и `(deck_sync_id, word_external_id)` в синхронизации.
- **Когда представлениям нужен независимый SRS?** Когда они проверяют разное воспроизведение (Image → Word и Word → Translation). Это требует ключа `(wordId, presentationId)`, миграции локальных таблиц и серверной таблицы событий. Поэтому это **отдельный, отложенный этап**.
- **Как сохранить старый прогресс?** Существующие карточки получают `presentationId = ""` (представление по умолчанию). Их ключ не меняется, история остаётся.
- **Что при редактировании и удалении представления?** Правка текста не сбрасывает расписание (как сейчас). Удаление представления удаляет только его единицу повторения, объект остаётся.

## 3. Минимальная целевая модель

```
Колода (deck)          + subject: "" (язык, по умолчанию) | "programming" | "science" | ...
  └─ Запись = Learning Object
        source   вопрос / термин / API / слово
        target   ответ / определение / перевод
        level    CEFR для языка; сложность (easy | medium | hard) для остальных
        code     (новое, только для подходящих предметов) код как текст, без исполнения
        tags, examples, image   как сейчас
  └─ Presentation      строится из записи + профиля предмета + направления, не хранится
  └─ Review unit       = запись (как сейчас); per-presentation позже
```

**SubjectProfile** — конфигурация в `core`, не отдельное приложение:
```js
{
  id: "programming",
  sides: "text",                 // язык не нужен
  fields: ["source", "target", "code", "tags", "difficulty"],
  difficulty: "general",         // не CEFR
  presentation: { front: ["context", "source", "code"], back: ["target", "examples"] },
  ai: { task: "concept" },
}
```
Профиль «language» описывает сегодняшнее поведение без изменений.

**Presentation** — список блоков, который строит чистая функция:
```js
buildCardPresentation(entry, deck, direction) → {
  front: [{ type: "meta", text: "JavaScript" }, { type: "text", role: "prompt", text: "Array.map()" }, { type: "code", text: "users.map(u => u.name)" }],
  back:  [{ type: "text", role: "answer", text: "A new array of names…" }],
}
```
Рендерер сопоставляет блокам общие компоненты Liora (крупный текст, код в `<pre>` с горизонтальной прокруткой, картинка, мета-строка). В React-компонентах нет `if (subject === …)`: выбор композиции делает профиль. Для языка блоки дают ровно то, что рисуется сегодня.

## 4. Границы local-first, ИИ и синхронизации

- Создание, правка, Learn, SRS, экспорт работают без сети и без ИИ (как сейчас).
- Новые предметные подсказки вызываются только из форм по кнопке. Планировщик ИИ не использует. Существующая языковая подсказка после «Снова» сохранена; в режиме картинки она не вызывается.
- ИИ только предлагает: ответ задачи `concept` (термин/вопрос, ответ, код, сложность, теги, 1–3 кандидата карточек) проверяется на сервере и в клиенте, показывается как предложение, которое можно принять, изменить или отклонить. Принятое становится обычными полями записи.
- От устаревших ответов защищают AbortController плюс сравнение ключа запроса с текущим вводом при получении ответа: asparagus → artichoke не получит старое обогащение.
- Синхронизация переносит только принятые данные: новые поля едут в существующем JSON-пакете колоды, серверных миграций для содержимого нет.
- Генерации изображений нет и не будет. ИИ может предложить в лучшем случае поисковый запрос (позже).

## 5. Медиа и совместимость

- Изображения — существующие локальные asset'ы (SHA-256, sync, экспорт). Новых систем нет.
- Старые колоды: без `subject` = язык; без `code` = как раньше. Хэш содержимого не меняется, пока новые поля пусты.
- **Риск:** десктоп 0.6.0 не знает `subject` и `code`. Если правка неязыковой колоды пройдёт через 0.6.0, эти поля потеряются при пересохранении. Митигация: выпустить десктоп 0.7.0 сразу вместе с этапом 1. Плюс 0.6.0 не сможет сохранить колоду без языков, то есть откажется её править, а не испортит молча (проверить).
- **Hub:** публикация неязыковых колод требует колонки `subject` на сервере (миграция, нужно согласие). До неё публикация таких колод в Hub закрыта.

## 6. Примеры

**Язык (без изменений):** asparagus → szparag, A2, noun, «I grilled some asparagus with olive oil and lemon.», теги food. Спереди слово, сзади перевод и пример.

**Программирование (пилот):** колода «JavaScript», subject = programming.
- Спереди: мета «JavaScript», вопрос «What does this return?», код `users.map(user => user.name)`.
- Сзади: «A new array of the users' names; map applies the callback to each element.»
- Сложность: medium. Код показывается моноширинным, с прокруткой, не исполняется и не интерпретируется как HTML.

## 7. Этапы

1. **Предмет колоды + пилот «Программирование» без ИИ.** `deck.subject`, профиль, поле `code`, сложность вместо CEFR, колода без языков, построение презентации + блок кода в Learn, поля в редакторе и «Добавить слова» по профилю, хранение (web + SQLite), экспорт/импорт, хэш, синхронизация, тесты. Десктоп 0.7.0.
2. **ИИ для неязыковых записей.** Задача `concept` в `suggest-word`, проверка, состояния (Думаю / Предложено / Проверьте / Ошибка / Нет сети / Лимит), защита от устаревших ответов, кандидаты 1–3 карточек.
3. **Языковой пилот с изображением.** Необязательная картинка у языковой записи, представление Image → Word рядом с Text → Translation (пока общее расписание), без регрессий старых колод.
4. **Независимые расписания представлений** — только если этап 3 покажет, что общее расписание мешает. Миграция ключей `review_cards` и событий прогресса.

**Отложено:** аудио, Science/History/Math/Law профили (направление задано, не реализуется), внешний поиск изображений, пакетное добавление неязыковых материалов, вход из URL/PDF, адаптивный выбор представления, предметная аналитика, публикация неязыковых колод в Hub.

## 8. Этап 1: что сделано

Этап 1 доказывает три вещи: обобщённую модель данных, предметно-зависимое представление и local-first без сети. ИИ в нём нет совсем.

**Модель.** Ядро записи общее (`source`, `target`, `tags`, `examples`). Всё предметное лежит в `subjectFields`, ключи которого задаёт профиль предмета (`core/usecases/subjects`). `code` есть только у профиля Programming и не является частью общей сущности. У колоды есть `subject` и `subjectFields` (для Programming это `technology`). Сложность (easy, medium, hard) вместо CEFR. Части речи и уровни остаются только у языка.

**Профиль решает всё, компоненты не знают предмет.** Профиль описывает:
- поля и их тип (text, code, choice);
- подписи, подсказки и ошибки (ключи сообщений);
- направления;
- нужны ли языки и ассистент;
- можно ли публиковать в Hub;
- блоки карточки.

React-компоненты читают эти флаги и блоки. Проверок `subject === …` в них нет.

**Представление.** `buildCardPresentation` строит блоки (meta, text, code, list). Для языка он возвращает `null`, и карточка рисуется ровно как раньше. Карточка Programming собрана по-другому:
- бумага в точку вместо линовки;
- шапка как полоса вкладок редактора: технология вкладкой, сложность делениями;
- вопрос строкой, под ним код панелью от края до края с номерами строк;
- термин без кода становится крупным заголовком;
- код показывается только на выбранной стороне: с вопросом (по умолчанию) либо с ответом;
- на синем обороте ответ, затем код, если выбрано «С ответом», и заметки;
- длинные строки кода переносятся, номер остаётся у начала исходной строки; многострочный ответ сохраняет переносы.

Код показывается текстом, никогда не исполняется и не читается как разметка.

**SRS не менялся.** Одна запись = одна единица повторения. Направление у Programming одно (вопрос → ответ).

**Хранение.**
- Web: поля в IndexedDB.
- Desktop: колонки `decks.subject`, `decks.subject_fields_json`, `words.subject_fields_json`.
- Пакет колоды, хэш содержимого, синхронизация, сессия Learn.

Новые поля пишутся только если не пусты, поэтому записи, файлы и хэши языковых колод не изменились (тесты). Пакет колоды с предметом получает `version: 2`. Приложение 0.6.0 и старые веб-клиенты такой пакет отклоняют («version 2 is not supported»), а не читают как языковую колоду с потерей кода (проверено на коде 0.6.0). Предмет выбирается, пока колода пуста; потом не меняется.

`subjectFields.codeSide` задаёт сторону кода (`back`, либо не записывается для `front`). Пакеты с `codeSide: back` получают версию 3: десктоп 0.7.0 их отклоняет, иначе он потерял бы настройку и раскрыл код ответа на вопросе. Языковые пакеты остаются версии 1, Programming без новой настройки остаётся версии 2. Хэш учитывает смену стороны.

**Создание и редактирование.** Programming доступен в меню «Новая колода»; выбор предмета стоит первым. Форма следует порядку «вопрос → необязательный код со стороной → многострочный ответ». Ctrl/⌘ + Enter добавляет карточку; Enter в ответе вставляет строку. Быстрое добавление сохраняет код и сторону уже существующих карточек. Подписи карточек, полей и подсказки берутся из профиля на всех 12 языках.

**Hub.** Публикация неязыковых колод закрыта в ядре (`canPublishToHub: false`), пункт меню скрыт. Серверных миграций нет.

**Проверки.**
- `pnpm check:subjects`: SQLite, сохранение, чтение, файл туда и обратно, сессия.
- Тесты веба и ядра.
- `pnpm check:offline-programming`: после первого визита сеть отключается. Затем: создать из меню → сохранить → закрыть → открыть → Learn → оценить → изменить сторону кода → открыть заново → быстро добавить карточку. Также проверяются перенос кода на 1280/390/844 px и обе темы. Проверяется, что ни одного запроса наружу и к ассистенту нет и что языковая карточка рядом рисуется как прежде.

**Попутно исправлено.**
- Service worker кэшировал сборку по адресам внутри `/app/`, которые на Vercel переписываются на HTML. Теперь пути от корня, кэш v4.
- Запись в колоду из «Быстрого добавления» больше не стирает предметные поля у остальных записей.

Офлайн-кеш v5: файлы сборки с хэшами загружаются из кеша независимо от `Vary: Origin`, без повторного запроса в сеть. Другие ресурсы сохраняют обычную проверку Vary.


## 9. Этап 2: предметные предложения и расширяемые профили

Профили лежат отдельно в `core/usecases/subjects/profiles`, каталог в `registry.js`. `SUBJECT_IDS` получается из каталога; выбор предмета использует общий Select с поиском при длинном списке. В компонентах нет переключения между двумя именами предметов.

Вместо одного `usesAssistant` профиль задаёт независимые возможности: `assistant.entry` (word/concept), `batch`, `description`, `reviewHint`. У Programming включена только задача concept. Формы размещают поля по `section: main/details`, а не по предположению, что основным полем всегда является код.

`conceptDrafts.js` используется и клиентом, и Edge Function. Схема JSON для модели строится из полей профиля. Тест с третьим профилем и полем `formula` проверяет, что контракт не зависит от Programming. Неизвестный предмет при импорте отклоняется до нормализации.

ИИ вызывается только по кнопке в редакторе (создание/правка) и быстром добавлении. Возвращает до трёх альтернатив одной карточки. Человек видит вопрос, ответ, предметные поля, заметки и теги, затем явно заполняет пустые поля и отдельно сохраняет карточку. Написанные поля, код и его сторона сохраняются. Есть состояния ожидания, предложений, проверки перед применением, отсутствия сети, входа, лимита и ошибки. AbortController и ключ полного черновика/колоды защищают от поздних ответов; размонтирование отменяет запрос.

Авторизация, дневная квота и ключ Gemini остаются на прежнем серверном пути. В Learn для Programming ИИ не включён. Принятые значения становятся обычной локальной записью; никакая генерация не нужна для дальнейшей учёбы.

### Добавление следующего предмета

1. Добавить профиль и включить его в `registry.js`. Указать поля колоды/записи, подписи, направления, блоки показа, возможности ИИ и медиа.
2. Использовать существующие типы полей и блоков; новый тип добавлять в общий обработчик/рендерер, а не веткой по имени предмета.
3. Добавить переводы, проверки нормализации, карточки, экспорта и обоих хранилищ. Не добавлять столбцы для отдельных предметных полей.
4. Если предыдущая версия приложения не понимает новую семантику, поднять читаемую версию пакета и задать `minPackageVersion` профиля/поля. Новые клиенты отклоняют неизвестные предметы; старые до этого изменения требуют защиты версией формата.
5. Сервер и клиент должны получить один и тот же каталог: concept не принимает схему и инструкции профиля от клиента.

## 10. Этап 3: необязательная картинка в обычной языковой колоде

Колоды с целой стороной «картинка» уже существовали. Этот этап не вводит новую систему изображений: использует прежние WordImageField, asset ID, SQLite/IndexedDB, экспорт и синхронизацию.

В обычной карточке сохраняются слово и перевод, а к ним можно добавить необязательную картинку (редактор и быстрое добавление). В настройках сессии появляется выбор Text → Translation / Image → Word, когда в колоде есть картинки. Второй вариант спрашивает слово на изучаемой стороне колоды. Карточки без картинки возвращаются к текстовому направлению. Переключение возвращает лицевую сторону, не создаёт единиц повторения и не меняет SRS.

Варианты объявлены в `studyPresentations` профиля, доступность необязательного изображения в `media.optionalImage`. Языковые карточки без изображения и прежние picture-side колоды работают по старому пути. Пакеты обычных текстовых колод с картинками теперь версии 4: старый редактор удалял такое изображение при сохранении, поэтому эти пакеты безопасно отклоняются старыми клиентами. Остальные языковые пакеты остаются версии 1, предметные версии 2/3 как прежде. Для нового режима нужен веб 0.8.0 или десктоп 0.8.0.

Проверки: общая тестовая база, `check:subjects`, `check:media`, `check:subject-assistant` (контролируемые ответы API, без расхода лимита), расширенный `check:offline-programming` (включает загрузку, сохранение, повторное открытие и оба режима языка без сети). SRS/FSRS и схемы событий прогресса не изменены. Реальные ответы Gemini не являются детерминированной частью тестов.

## 11. Язык ответов и единое создание (0.8.1)

Любой профиль с пояснениями может подключить `CONTENT_LANGUAGE_FIELD` и указать `assistant.languageField`. Язык хранится в `deck.subjectFields`, виден в редакторе, быстром создании и предложениях ИИ. Начальный выбор новой колоды берётся из языка интерфейса и сразу показан пользователю. Для существующей колоды язык не подставляется: перед новым запросом ИИ требуется явный выбор. Изменение настройки не переводит сохранённые записи. Сервер предпочитает язык колоды старому `writeIn`, который остаётся совместимым со старыми клиентами.

Быстрое создание выбирает тему из каталога и показывает поля профиля. Сохранение и отмена добавления сохраняют предметные поля колоды. Отдельного пункта Programming в меню создания больше нет. Смена темы/колоды отменяет незавершённые запросы.

Пакеты с языком ответов имеют версию 5. Минимальная версия теперь учитывает поля колоды, а также профиля и записи. Старые редакторы отклоняют такой пакет вместо потери настройки. Схема Gemini исключает пустые варианты enum и пустые объекты свойств. Живой запрос Hoisting проверен в продакшен-приложении, дополнительно проходят проверки контрактов, хранения и браузерные сценарии.

## 12. Новые предметы и оформление по технологии (0.9.0)

Каталог содержит Language, Programming, Mathematics и History. Новые предметы подключаются своим профилем, полями, композициями блоков, формой и инструкциями ассистента. Общие компоненты не выбирают между фиксированными именами предметов.

- Mathematics: область, язык ответов, формула LaTeX с выбором стороны, шаги решения и сложность. Формула имеет предварительный просмотр в форме и читаемую отрисовку на карточке; неверный синтаксис остаётся обычным редактируемым текстом. В вопросе, ответе, заметках и шагах решения LaTeX можно писать внутри `$...$` или `\(...\)`, а отдельное уравнение внутри `$$...$$` или `\[...\]`. Запись с ошибкой остаётся текстом; цены и фрагменты кода не интерпретируются как формулы. KaTeX загружается лениво, не разрешает доверенные HTML-команды и использует локальные шрифты. Карточка оформлена как тетрадь в клетку с отдельной областью вычислений.
- History: период, язык ответов, контекст вопроса, дата и последствия. Дата и последствия не раскрываются до ответа. Карточка оформлена как архивный лист с засечками, штампом даты и линией событий.
- Programming: существующее свободное поле Technology автоматически выбирает подходящее оформление и подписи. SQL и основные диалекты, CSS, PHP, JavaScript, Rust, Java, C++, C и C# имеют собственные вкладки и детали панели кода в общем спокойном стиле редактора. Другие технологии сохраняют общую карточку программирования. Нового уровня классификации и сохранённого поля темы нет.

`appearances.js` применяет частичные переопределения из каталога профиля. `appearanceField` указывает существующее поле колоды; `appearances` задаёт его псевдонимы и переопределения оформления, подписей и инструкций ИИ. Новую технологию (например Python или Rust) добавляют описанием и стилем, без изменения механизма выбора или компонентов. Это необязательная возможность любого будущего предмета, а не особый переключатель Programming. Версия после названия технологии учитывается при распознавании. Исходная технология сохраняется полностью и передаётся ИИ.

Для новых предметов минимальная версия пакета 6. Старые приложения отклоняют такие колоды вместо удаления предметных полей. Хранение, экспорт, импорт и повторное открытие проверяются для IndexedDB и SQLite. Новая композиция не создаёт дополнительных единиц повторения. SRS/FSRS не меняются.

`check:offline-knowledge` проверяет создание и повторное открытие новых предметов, формулы и шрифты без сети, быстрое создание, обе темы, мобильную ширину и клавиатуру селектора. `check:technology-appearances` проверяет девять оформлений и неизвестную технологию на десктопе и телефоне. Контракты ассистента проверяют серверные инструкции и выбранный язык; результаты реального провайдера не подменяются этими тестами.
